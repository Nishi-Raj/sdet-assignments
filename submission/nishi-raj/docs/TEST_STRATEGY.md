# Test Strategy — Subscription & Billing Service

## Objective
Prove that subscription lifecycle behavior is correct across HTTP APIs, domain state transitions, persistence, webhook delivery, and the external payment-provider boundary.

## Assumptions and scope
- This repository contains a minimal TypeScript service fixture because the assignment does not provide a runnable service implementation.
- The fixture is deliberately small and exists to make the test strategy executable; it is not production billing software.
- `basic` and `pro` plans have fixed USD prices and trial periods (basic: $19 / 7 days; pro: $49 / 14 days). Both begin in `trialing` for this exercise.
- Persistence is an isolated in-memory repository. Each test resets mutable data and seeds one known customer.
- Webhook signatures use HMAC-SHA256 over the exact raw request body and a test-only secret.
- Provider calls are represented by an injected fake. No real payment network is contacted.

## Validation levels
1. API contract: create, retrieve, cancel, request validation, HTTP status and response body.
2. Domain/state machine: valid lifecycle transitions and rejected transitions.
3. Persistence: subscription, invoice, webhook-event and audit records; API/database consistency.
4. Integration boundary: provider call arguments/outcomes and signed inbound webhook requests.
5. End-to-end: API/webhook request through domain logic to persisted side effects.

## Scenario strategy
| Area | Key scenarios | Critical assertions |
|---|---|---|
| Creation | valid plan, unknown plan/customer, missing fields, wrong payment method | HTTP response, no unintended record or charge |
| Lifecycle | trial success/failure, retry success, cancellation | legal state and audit history |
| Webhooks | valid signature, forged signature, malformed body | reject invalid requests before persistence |
| Idempotency | same event ID delivered twice | one transition, one invoice, one event record, no repeated side effect |
| Ordering | failure after success; success after cancellation | stale/illegal event ignored without regression |
| Persistence | invoice and subscription state | stored records agree with externally visible state |
| Provider | success, decline, timeout | deterministic fake outcomes and exact arguments |

## Design patterns
- **State Machine:** `SubscriptionStateMachine` owns the transition table; illegal transitions throw rather than allowing arbitrary status mutation.
- **Builder:** `SubscriptionBuilder` and `WebhookBuilder` create readable test data with safe defaults.
- **Strategy / Dependency Injection:** `PaymentProvider` is an interface; `FakePaymentProvider` is injected and records calls/outcomes.
- **Repository:** `InMemoryBillingRepository` isolates persistence operations from service and test logic.
- **Factory-style fixture:** `tests/fixture.ts` composes repository, provider, service, Express app and Supertest client once for consistent isolated tests.

## Database entities and invariants
- `subscriptions`: current plan/status and timestamps.
- `invoices`: amount, status, subscription link and provider reference.
- `webhookEvents`: event ID deduplication and processing outcome.
- `audit`: each accepted state transition with prior/new state and reason.

Invariants asserted include: canceled subscriptions never reactivate; a duplicate event ID does not create a second invoice or transition; late failed payment cannot regress an active subscription; invalid signatures create no event or invoice; and API-visible status equals persisted subscription status.

## Test data isolation
Each test clears subscription, invoice, webhook and audit collections, then seeds a known customer. Provider call history and configured outcome are reset. IDs are generated by the service fixture, avoiding dependence on records from earlier tests.

## What is real vs mocked
- Real within the fixture: Express HTTP routing, request parsing, HMAC verification, domain transition logic, service orchestration and repository behavior.
- Mocked: external payment provider and durable database. The in-memory repository is a test persistence adapter, not a claim of database-engine coverage.
- Simulated: provider-originated webhook deliveries, including signed, forged, duplicate and out-of-order events.

## Limitations and next steps
- The fixture is single-process and in-memory; it does not prove transaction isolation, crash recovery, cross-instance idempotency, or database constraints.
- Concurrent duplicate webhook delivery should be tested against a transactional database with a unique constraint on event ID.
- Provider timeout behavior is represented at the provider contract seam; a production implementation should define retry and reconciliation semantics for unknown charge outcomes.
- Additional production hardening would include schema validation, currency/amount checks against invoice records, structured logging, and contract tests against a real persistence adapter.
